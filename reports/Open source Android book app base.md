# Assemble the book app from parts, not forks

No open-source project can serve as a turnkey fork for this app. Every mature, feature-complete reading tracker is copyleft (GPL), Flutter, or Java/XML. The permissive Kotlin + Compose trackers are either small (sriniketh/prose, Apache-2.0, 1 star) or very young (tn3w/Shelf, MIT, about two months old with no Room or Hilt). No open-source Android book tracker syncs with Supabase. The build plan is therefore to assemble the app. Use **Now in Android or prose** as the architectural skeleton and **Shelf (MIT)** as the main feature reference to copy from. Build on Google's official, actively maintained libraries: CameraX 1.7.0, ML Kit, Photo Picker, WorkManager 2.12.0, Material 3 1.5.0 (Expressive is now stable) and Navigation 3 1.2.2. Copy the Gemma pipeline almost wholesale from **Google AI Edge Gallery** (Apache-2.0) on **LiteRT-LM 0.19.1**. Write the sync layer yourself: a small custom last-write-wins sync between Room and Supabase through supabase-kt 3.9.0. By my estimate that is a few hundred lines of code, and it avoids running PowerSync as a second hosted service. Two findings should change the product design. First, Gemma should not invent a book summary from a front cover. Have it extract title and author, fetch the real description from Open Library or Google Books, and only then summarize. Second, Supabase's free tier has no backups and pauses after about a week of inactivity, so an in-app JSON+covers export is required, not a nice-to-have.

## Every candidate fork base fails at least one of license, stack or maturity

A GitHub API survey on 2026-11-21 found many book apps but almost none that are Kotlin + Compose, active and permissively licensed at once. The closest matches are below.

**Prose** is the most fork-worthy codebase. It has `core-*` and `feature-*` modules, unidirectional data flow, Hilt wiring, Room, Retrofit with kotlinx.serialization, and ML Kit text recognition ([prose README](https://github.com/sriniketh/prose)). It lacks reading statuses, stats, barcode scanning, import and sync, so most of the product would still have to be built. It is also a one-person, one-star project, so forking it means inheriting unreviewed code. A cleaner option is to scaffold from **Now in Android** (Apache-2.0, about 22k stars). It is the canonical Room + WorkManager + Compose module layout and ships baseline profiles ([nowinandroid](https://github.com/android/nowinandroid)). Use prose as a smaller, book-shaped example of the same pattern.

**Shelf** has the richest features among permissive projects. It offers barcode and on-device cover recognition, want/reading/finished statuses, shelves and genres, daily goals, streaks, monthly stats, a "year in books" recap, Goodreads/StoryGraph CSV import and folder backup. Its source has files named `Csv.kt`, `Scan.kt`, `Recognizer.kt`, `Stats.kt` and `Wrapped.kt` ([Shelf](https://github.com/tn3w/Shelf)). It is a bad fork base for three reasons. It uses one `ShelfViewModel` with no DI and no Room. It bundles an EPUB/PDF reader, audiobooks and native TTS code that this app does not need. It is also only two months old. Port individual algorithms from it with MIT attribution. ReadTracker has good page-checkpoint, ETA and heatmap UX, but it has **no license file**, which legally means "all rights reserved". Study it, but don't copy it.

The GPL projects are still useful as feature specs. Openreads has four lists including DNF, custom tags, a documented CSV format at `doc/csv.md`, and Goodreads/BookWyrm import. Openshelf has five statuses, smart shelves and a four-step ISBN lookup. NeverTooManyBooks supports about 19 metadata sources and batch barcode scanning ([NTMB](https://github.com/tfonteyn/NeverTooManyBooks)). Copying their code into a private app that is never distributed creates essentially no obligation. Shipping that app to anyone else, even as a sideloaded APK, would force the whole app under GPL. The safe rule is to read GPL code for ideas and copy only Apache-2.0 or MIT code. This is not legal advice.

## Google's own libraries already cover capture, scanning and batch import

**ISBN scanning has two tiers.** For a quick one-book scan, the **Google Code Scanner** (`play-services-code-scanner:16.1.0`) needs no camera permission and no camera UI. Call `startScan()` restricted to `FORMAT_EAN_13` and read `rawValue` ([ML Kit Code Scanner](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner)). For a branded scanner with an animated overlay and continuous shelf scanning, use **CameraX 1.7.0** (released 2026-11-18). Its `camera-compose` artifact provides `CameraXViewfinder` with built-in pinch-to-zoom and tap-to-focus, and `camera-mlkit-vision` provides `MlKitAnalyzer` to feed frames to the bundled ML Kit barcode model (`barcode-scanning:17.3.0`, about 2.4 MB) ([CameraX releases](https://developer.android.com/jetpack/androidx/releases/camera); [ML Kit Barcode](https://developers.google.com/ml-kit/vision/barcode-scanning/android)). The same CameraX pipeline captures cover photos. Prefer the bundled model to the 200 KB unbundled one, because unbundled scans **silently return nothing until Play services finishes downloading the model**. Accept only checksum-valid EAN-13 codes starting with 978 or 979, which rejects price stickers.

**Batch import of 30-50 gallery photos** uses `PickMultipleVisualMedia(maxItems)` from `activity-compose` 1.13.0. Read the platform cap from `MediaStore.getPickImagesMaxLimit()` instead of hardcoding it. Call `takePersistableUriPermission` on each URI, because grants otherwise expire when the app stops ([Photo picker](https://developer.android.com/training/data-storage/shared/photopicker)). Persist the URIs to a Room `import_queue` table. Then let one WorkManager 2.12.0 `CoroutineWorker` process each photo in order: downscale it, try `InputImage.fromFilePath` through the barcode scanner, fall back to OCR or Gemma, and look up metadata at Open Library's rate limit. The UI watches progress through `getWorkInfosForUniqueWorkFlow`. The OCR fallback is **ML Kit Text Recognition v2** (`text-recognition:16.0.1`, about 4 MB per script bundled). It returns lines with bounding boxes, and the tallest line is usually the title ([ML Kit Text Recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)). Google's [mlkit samples](https://github.com/googlesamples/mlkit) and [camera-samples](https://github.com/android/camera-samples) (both Apache-2.0) are the code to copy here.

**Metadata should come from Open Library first.** It needs no API key. It allows 1 request per second by default, or 3 per second if you send a User-Agent with an app name and contact ([Open Library API](https://openlibrary.org/developers/api)). In a live test on 2026-11-21 it resolved Italian, German, French and Spanish ISBNs ([direct test](https://openlibrary.org/api/books?bibkeys=ISBN:9788845292613&format=json&jscmd=data)). A Japanese test ISBN returned 404, but that ISBN was only checksum-valid and never confirmed as assigned, so non-Latin coverage remains untested rather than shown to be poor. Its Covers API **limits ISBN-based cover lookups to 100 per IP per 5 minutes**, while lookups by cover ID are unlimited. During a batch import, take `cover_i` from the edition response and request `/b/id/{id}-M.jpg` ([Covers API](https://openlibrary.org/dev/docs/api/covers)). Google Books is the fallback, but it effectively needs a key: a keyless request during this research got HTTP 429 from a shared, exhausted quota ([Google Books API](https://developers.google.com/books/docs/v1/using)). Neither API has a mature Kotlin client, so write a small Retrofit or Ktor interface. Load covers with **Coil 3.6.3** plus `coil-network-okhttp`, and share the OkHttp client that carries the identifying User-Agent ([Coil](https://github.com/coil-kt/coil)).

**The "new books" RSS feed** uses **prof18 RSS-Parser 6.2.0**. It is Apache-2.0, coroutine-based, parses RSS, Atom and RDF, and was released 2026-11-08 ([RSS-Parser](https://github.com/prof18/RSS-Parser)). Rome has not released since March 2023. RSS-Parser dropped caching in 6.0, so store feed items in Room. These free feeds were confirmed live: [Book Riot new books](https://bookriot.com/category/new-books/feed/), [NYT Books](https://rss.nytimes.com/services/xml/rss/nyt/Books.xml), [Lit Hub](https://lithub.com/feed/), [Kirkus](https://www.kirkusreviews.com/feeds/rss/), [Reactor](https://reactormag.com/feed/), [Publishers Weekly](https://www.publishersweekly.com/pw/feeds/recent/index.xml) and [Porchlight's Atom feed](https://www.porchlightbooks.com/blogs/new-releases.atom). Penguin Random House's `/feed/` returns HTML. For a personal "new from authors I follow" feed, poll Open Library `search.json?author_key=<OLID>&sort=new` daily and diff against stored work keys. Filter by language, because `sort=new` also surfaces new translations ([Search API](https://openlibrary.org/dev/docs/api/search)).

**Profile stats and badges** need little from outside. Use **Vico 3.3.1** stable (Apache-2.0, about 3.2k stars, very active) for a books-per-month column chart. Its pie charts are still marked experimental ([Vico guide](https://guide.vico.patrykandpatrick.com/getting-started.md)). Build goal rings from `CircularProgressIndicator` or the now-stable `WavyCircularProgressIndicator`. No achievements library with real adoption exists. Define badges as data rows (metric plus threshold), evaluate them after each status change, and store unlocks in Room. Habitica shows the pattern, but its code is GPL ([habitica-android](https://github.com/HabitRPG/habitica-android)).

## Gemma 4 should read the cover, not write the blurb

**Google AI Edge Gallery** is the single most reusable codebase in this whole stack. It is Apache-2.0 and Kotlin/Compose/Hilt/WorkManager. It runs Gemma 4 E2B and E4B with image input on LiteRT-LM ([Gallery](https://github.com/google-ai-edge/gallery)). Three parts lift almost directly. `worker/DownloadWorker.kt` and its `data/Download*` siblings handle the multi-GB model download. `ui/llmchat/LlmChatModelHelper.kt` wraps the engine and conversation. The allowlist JSON pins exact Hugging Face commit hashes for each model file. Gallery also has an `AICoreModelHelper` backend for Gemini Nano ([repo tree](https://github.com/google-ai-edge/gallery/tree/main/Android/src/app/src/main/java/com/google/ai/edge/gallery)). Gallery's image path encodes each bitmap as TGA into `Content.ImageBytes` and puts images before text "to ensure proper autoregressive token sequencing". It also always caps `maxOutputToken`, because a JSON schema that allows unlimited whitespace can decode until the KV cache is full ([LlmChatModelHelper.kt](https://raw.githubusercontent.com/google-ai-edge/gallery/main/Android/src/app/src/main/java/com/google/ai/edge/gallery/ui/llmchat/LlmChatModelHelper.kt)).

Pin **`litertlm-android:0.19.1`** (2026-11-05). That release added Gemma 4 vision and audio on the GPU ("Artisan") backend ([LiteRT-LM releases](https://github.com/google-ai-edge/LiteRT-LM/releases)). The Kotlin API supports constrained output through `ResponseFormat.json(schema)` once `ConversationConfig(enableResponseFormat = true)` is set ([ResponseFormat.kt](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/main/kotlin/java/com/google/ai/edge/litertlm/ResponseFormat.kt)). It also exposes a Gemma-4-only `ExperimentalFlags.visualTokenBudget` of 70 to 1120 tokens ([ExperimentalFlags.kt](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/main/kotlin/java/com/google/ai/edge/litertlm/ExperimentalFlags.kt)). Watch three pitfalls. LiteRT-LM 0.17 and later carry Kotlin 2.4 metadata and **fail to compile under Kotlin 2.2**. The GPU backend needs `libOpenCL.so` and `libvndksupport.so` `uses-native-library` manifest entries. `engine.initialize()` can take about 10 seconds ([getting_started.md](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/main/docs/api/kotlin/getting_started.md); [Android docs](https://developers.google.com/edge/litert-lm/android)). MediaPipe LLM Inference is deprecated on Android, and Google directs developers to LiteRT-LM ([LLM Inference guide](https://developers.google.com/edge/mediapipe/solutions/genai/llm_inference/index)).

The model choice is a RAM and accuracy tradeoff:

| | Gemma 4 E2B | Gemma 4 E4B |
|---|---|---|
| `.litertlm` size | 2.58 GB | 3.66 GB |
| Gallery minimum device RAM | 8 GB | 12 GB |
| S26 Ultra GPU decode / TTFT (text) | 52.1 tok/s / 0.3 s | 22.1 tok/s / 0.8 s |
| OmniDocBench edit distance @1120 visual tokens (lower is better) | 0.290 | 0.181 |
| Same @280 visual tokens | 0.496 | 0.307 |

Sources: [E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm), [E4B card](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm), [Gallery allowlist](https://raw.githubusercontent.com/google-ai-edge/gallery/main/model_allowlists/1_0_23.json), [Gemma 4 Technical Report](https://arxiv.org/html/2607.02770v1).

The resolution numbers matter most. Cutting the visual budget from 1120 to 280 tokens nearly doubles E2B's document error, so **run covers at 560-1120 visual tokens** and default to E2B, with E4B offered on 12 GB+ phones. Gemma 4 is **Apache-2.0**, the first Gemma under that license ([Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/gemma-4/)). The current E4B card says its repo is not gated, so the app can download from a pinned HF commit URL or a self-hosted mirror without Gallery's Hugging Face OAuth setup. A May dev.to post claimed the E2B repo was gated, so verify that before shipping ([dev.to](https://dev.to/samdude/gemma-4-on-android-tricks-for-faster-on-device-inference-3kj5)).

Latency on mid-range phones is the biggest unknown. The only image-stage measurement found comes from a Qualcomm IoT board, where the vision encoder took **about 8 s on CPU and 20 s on NPU** ([LiteRT-LM #2187](https://github.com/google-ai-edge/LiteRT-LM/issues/2187)). One community write-up adds more risks: silent fallback from GPU to CPU, NPU crashes on some devices, and a claimed 2-5 tok/s decode on CPU-only mid-range phones. That last figure is the author's claim and names no device ([dev.to](https://dev.to/samdude/gemma-4-on-android-tricks-for-faster-on-device-inference-3kj5)). That makes Gemma an enrichment step for the batch queue rather than something the user waits on. It also argues for a hybrid pipeline. Run ML Kit OCR first as a cheap gate and grounding text. Have Gemma vision return `{title, author}` under a JSON schema. Look up the real description through Open Library or Google Books, then have Gemma summarize that retrieved text with thinking disabled. Obscure or non-English titles may return no description. For those, fall back to a short paragraph generated from the cover, the OCR text and any back-cover photo the user captures, and label it in the UI as "generated from cover", or leave the field blank for manual entry. A front cover does not contain the synopsis, so asking a 2B model to "write a summary" from the image invites hallucination. **AICore** with Gemma 4 / Gemini Nano 4 through the ML Kit GenAI Prompt API is Google's preferred production path. It avoids the 2.6 GB download and uses the NPU, but as of November 2026 it was still a developer preview limited to recent flagships ([AICore blog](https://developer.android.com/blog/posts/announcing-gemma-4-in-the-ai-core-developer-preview)). Treat it as an optional fast path behind the same interface Gallery already defines. On devices below 8 GB RAM, skip Gemma entirely and use OCR plus a metadata lookup.

## Supabase sync is a gap you must fill yourself, and that is fine

No open-source Android book tracker uses Supabase. Firebase appears only in small or stale projects such as [ninova](https://github.com/armutyus/ninova). GitHub repo searches for Supabase book apps returned nothing relevant ([GitHub search](https://github.com/search?q=supabase+book&type=repositories)). The client to use is **supabase-kt 3.9.0** (MIT, about 855 stars, released 2026-11-03). It provides `auth-kt`, `postgrest-kt`, `storage-kt` and `realtime-kt` under a BOM, plus `compose-auth` for native Google sign-in through Credential Manager. It needs Ktor 3.x and minSdk 26 ([supabase-kt](https://github.com/supabase-community/supabase-kt); [install docs](https://supabase.com/docs/reference/kotlin/installing)). It is still a community project, with a stated plan to become official.

For one user, a few thousand books and two or three devices, the right design is **Room as the source of truth with a custom last-write-wins sync**. Every synced row carries a client-generated UUID, `user_id default auth.uid()`, a server-trigger-set `updated_at`, and a `deleted` tombstone. A WorkManager job upserts dirty rows, then pulls rows where `updated_at > lastPulledAt`. Because the server sets the timestamps, device clock skew cannot corrupt the pull cursor. Conflicts happen only when you edit the same book on two offline devices, so per-row LWW is acceptable. **PowerSync** is the batteries-included alternative. Its Kotlin SDK is Apache-2.0 and has a Supabase connector, a Room integration and an [Android Supabase demo](https://github.com/powersync-ja/powersync-kotlin). It adds a second hosted service, though: the free tier deactivates after about a week of inactivity, and paid plans start at **$49/month** ([PowerSync pricing](https://www.powersync.com/pricing)). Keep it in reserve for the day the app adds sharing between users. ElectricSQL has no Kotlin client ([Electric docs](https://electric.ax/docs/guides/client-development)). [supabase-offline-kt](https://github.com/nesfeder/supabase-offline-kt) (MIT, targets supabase-kt 3.9) implements an ordered offline write queue and is worth reading. With 2 stars, it is too risky to depend on.

Covers go in a **private Storage bucket at `{uid}/{bookId}.webp`**, with owner-only RLS on `storage.objects`. Upsert requires both SELECT and UPDATE policies ([Storage access control](https://supabase.com/docs/guides/storage/security/access-control)). Resize to about 600 px on the device before uploading, because Image Transformations are unavailable on the Free plan. At 100-200 KB per cover, the plan's **1 GB of storage** holds 5,000-10,000 covers, and the 500 MB database is far more than book rows need ([billing docs](https://supabase.com/docs/guides/platform/billing-on-supabase)). The free tier has two operational traps. Projects **pause after about a week without activity**. They remain restorable for a year, but sync fails until you resume them, so the app must treat a paused backend as offline ([project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)). The Free plan also has **no automatic backups and no PITR**, and database backups never include Storage objects. Supabase itself tells free users to export regularly ([backups docs](https://supabase.com/docs/guides/platform/backups)). Every device holds a full Room copy, which gives one layer of redundancy. Add an in-app export as the real backup: Room tables serialized to JSON with kotlinx.serialization, zipped with the cover files, and saved through the Storage Access Framework, with a matching import that merges by ID. That export doubles as the migration path off Supabase.

## Material 3 Expressive went stable in November 2026, so the motion layer needs little custom work

**material3 1.5.0** (2026-11-18, in Compose BOM 2026.11.01) graduated the Expressive APIs to stable ([material3 releases](https://developer.android.com/jetpack/androidx/releases/compose-material3)). That covers `MotionScheme.expressive()/standard()`, the expressive theme, ButtonGroup, SplitButton, the FAB menu, FloatingToolbar and the wavy progress indicators. Still experimental are `LoadingIndicator`/`ContainedLoadingIndicator`, `PullToRefreshDefaults.LoadingIndicator`, and `MaterialShapes` with `toShape()`. Version 1.4.0 contains none of the Expressive APIs, so 1.5.0 is the floor. Wrap the app in `MaterialExpressiveTheme(motionScheme = MotionScheme.expressive())` and pull every spring from `MaterialTheme.motionScheme`. Use spatial specs for bounds and effects specs for color and alpha, which keeps overshoot off fades ([MotionScheme](https://developer.android.com/reference/kotlin/androidx/compose/material3/MotionScheme)). In the book app, the status filter becomes a ButtonGroup, "Add book" becomes a FAB menu (scan / search / manual / import), and reading progress uses a wavy indicator.

**Pull-to-refresh tension** is `PullToRefreshBox` with a custom indicator that reads `state.distanceFraction` inside `graphicsLayer`. Translate the list by a diminishing-returns curve and fire `HapticFeedbackType.GestureThresholdActivate`, which exists for exactly this gesture, when the fraction crosses 1 ([pull-to-refresh guide](https://developer.android.com/develop/ui/compose/components/pull-to-refresh); [HapticFeedbackType](https://developer.android.com/reference/kotlin/androidx/compose/ui/hapticfeedback/HapticFeedbackType)). Lazy lists already get the Android 12+ stretch overscroll. For a custom rubber band, the official `OffsetOverscrollEffect` sample shows the pattern: 0.1× resistance on user-input deltas, then a velocity-preserving `spring()` settle after the fling ([OverscrollEffect](https://developer.android.com/reference/kotlin/androidx/compose/foundation/OverscrollEffect)). **Swipe-to-change-status** maps to `anchoredDraggable` with three anchors, `SegmentTick` haptics on anchor change and `Confirm` on commit ([drag/swipe guide](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/drag-swipe-fling)).

**Predictive back** is on by default for apps targeting Android 15+. Navigation 3 1.2.0 added `NavigationBackHandler` for custom components ([predictive back setup](https://developer.android.com/develop/ui/compose/system/predictive-back-setup); [navigation3 releases](https://developer.android.com/jetpack/androidx/releases/navigation3)). Avoid a root-level `BackHandler`, which kills the back-to-home animation. **Shared element transitions** from the cover grid to the detail screen wrap `NavDisplay` in `SharedTransitionLayout`. Apply `sharedElement` keyed on `"cover-${book.id}"` to the image, take the animated scope from `LocalNavAnimatedContentScope.current`, and use `sharedBounds` for the card and title ([shared elements with navigation](https://developer.android.com/develop/ui/compose/animation/shared-elements/navigation)). A back swipe then scrubs the cover back into its grid cell. **Androidify** is the code to copy for the polish layer: the theme setup, the `LocalSharedTransitionScope` provider, a shape-morphing `sharedBoundsRevealWithShapeMorph`, and a `MaterialShapes.Cookie9Sided` CameraX capture button with motion-scheme press-scale ([Androidify blog](https://android-developers.googleblog.com/2025/05/androidify-building-delightful-ui-with-compose.html); [android/androidify](https://github.com/android/androidify)). Androidify still pins a 1.5.0 alpha, so upgrade its snippets to 1.5.0 stable. To keep the motion smooth, read animated values only in deferred lambdas (`offset {}`, `graphicsLayer {}`, `drawBehind {}`), key lazy items by ID, and ship a baseline profile as Androidify and Now in Android do. [Mihon](https://github.com/mihonapp/mihon) (Apache-2.0) is the closest cover-grid library app for density, selection mode and category tabs.

## Conclusion

Nobody has published this app because it is several apps in one: a tracker, a scanner, a sync client and an on-device VLM host. Each of those parts is now solved separately by Google-maintained, permissively licensed code, and that matters more for this build than any fork base would. The two hardest pieces are Gemma and motion. Gallery and Androidify are reference implementations from the platform owner, and both are better maintained than any book app surveyed. The uniquely book-specific work is therefore small: the data model, the lookup chain, the badge rules and a small sync worker.

The real risks are operational, not licensing. Gemma vision latency on non-flagship phones is unmeasured. A 2.6 GB first-run download needs Wi-Fi, storage and RAM gating. supabase-kt is still community-maintained. The Supabase free tier pauses itself and keeps no backups. Before building UI, prototype three things on your actual phone: one cover through LiteRT-LM at 1120 visual tokens with a JSON schema, one batch of 40 photos through the WorkManager queue, and one push/pull sync cycle against a free Supabase project. Those three measurements decide whether Gemma runs inline or as background enrichment, and whether the free tier is enough.
